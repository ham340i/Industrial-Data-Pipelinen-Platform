# Refactoring 

The refactoring of the code in this project will be based on the SOEN 490 requirements and issues from Sonar Cloud Code analysis. All refactoring changes should not affect tests results and should not impact the app. 

## Code Quality Rubric Checks
The following refactoring checks taken from the SOEN 490 Code Quality Rubric
| Checks | Description |
|---|---|
| File size | Source files should generally remain at or below 500 lines of code. |
| Function/method size | Functions and methods should generally remain at or below 50 lines of code. |
| Cyclomatic complexity | Functions and methods should have cyclomatic complexity of 15 or less. |
| Class responsibilities | If object-oriented programming is used, each class should have one primary responsibility and should not combine substantially unrelated responsibilities. |
| Coupling | Classes, modules, and components should avoid unnecessary dependencies, circular dependencies, and unnecessary cross-layer dependencies. |
| Cohesion | Methods and data grouped within a class, module, or component should serve a related purpose; unrelated functionality should not be grouped together solely for convenience. |
| Code duplication |  Identical or near-identical blocks of 20 or more lines should not appear in three or more locations, and repeated domain/business rules should normally have a single source of truth. |
| Unfinished and unused code | Important source code should not contain unresolved TODO/FIXME items for required functionality, NotImplemented or equivalent placeholders, placeholder return values, large commented-out replacement implementations, clearly unused source files/classes/functions, or duplicate alternative implementations. |
| Architecture documentation | The project wiki includes an up-to-date high-level architecture diagram showing the major system components or layers and their relationships. Relevant class or domain diagrams are included where appropriate. The diagrams must be reasonably consistent with the implemented system. For later releases, teams may document material architecture changes rather than recreating diagrams that have not changed. |
| Naming conventions | The project follows consistent naming conventions for files, classes, functions/methods, variables, and other relevant code elements. The conventions must be documented in the project wiki or linked to an established language or framework standard that the project follows. |
| Performance considerations | Where performance is relevant to the project, the project wiki identifies important performance requirements or potential bottlenecks and describes the architectural or implementation approach used to address them. The documented approach must be reasonably consistent with the implemented system. |

Generated code, vendored libraries, generated migrations, generated fixtures, and other automatically generated files are excluded from these refatoring checks.

## Sonar Cloud Code analysis

The issues generated by tend to overlap with the rubric checks above. For issues that are not covered by the checks above, if Sonar Cloud Code marks them as security or Reliability issues, then they should be addressed. Maintainablity issues not covered by the checks will be considered low priority. 

## Exceptions

If the code intentionally requires any of the critera to be unsatisfied, then it must be documented. 
These documents should include the affected file, the affected lines of code, the reason for the design decision, the related pull request (if applicable), and the username of the contributor. 
The reasoning should have concrete purpose for the code.
